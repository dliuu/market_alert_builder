# 07 — Decision log

Append-only. Each entry: what was decided, what it rules out, and what would reverse it.

---

**D1 — Brief-as-object, not brief-as-template**
The pipeline emits versioned JSON; web and email are renderers over it.
*Rules out:* generating HTML directly from the compute stage.
*Reverses if:* never. Retrofitting this means parsing your own prose to recover the claim history.

---

**D2 — The LLM never produces a number**
Narration writes prose only; figures are substituted from the object.
*Rules out:* asking the model to summarise raw market data.
*Reverses if:* never, for a tool you act on. A hallucinated basis point is a worse failure than a missing paragraph.

---

**D3 — Tape quality runs on daily OHLCV**
Range position is exact from daily O/H/L/C; RVOL uses 30-day average volume.
*Rules out:* gap-fill behaviour and VWAP in v1.
*Reverses if:* you notice yourself repeatedly wanting to know whether a gap filled. Then buy minute bars (~$29/mo).

---

**D4 — Two services, Postgres as the shared surface**
Next.js for UI/auth/billing/email templates; Python for the pipeline.
*Rules out:* a single-language monolith; an internal REST API between the two.
*Reverses if:* this stays single-user forever, in which case a Python monolith with Jinja is less to operate.

---

**D5 — Python owns the schema exclusively**
Alembic is the only migration path; the web app introspects and never issues DDL.
*Rules out:* Drizzle or Prisma migrations.
*Reverses if:* never. Two ORMs owning one schema is the most reliable way to lose a weekend.

---

**D6 — One HTTP call between services: `/api/render/:brief_id`**
So the email template has exactly one source (React Email in the web app).
*Rules out:* a parallel MJML template in Python.
*Reverses if:* the web app's availability becomes the pipeline's bottleneck. Fallback is a plaintext-only send.

---

**D7 — `user_id` on every table from the first migration**
Even during single-user development.
*Rules out:* nothing. Costs one column.
*Reverses if:* never.

---

**D8 — End-of-day data, not real-time**
The close brief is EOD-native; the open brief uses prior close plus delayed pre-market.
*Rules out:* intraday alerts, live dashboards.
*Reverses if:* you take the product commercial and buy a real-time redistribution licence — a business decision, not a technical one.

---

**D9 — No intraday alerts**
*Rules out:* push notifications, a third send.
*Reverses if:* never. It changes a briefing into a monitor, which is a different product with worse habits attached.

---

**D10 — Supabase for Postgres, not Neon**
Managed Postgres from Supabase. The worker still owns the schema via Alembic against the direct connection; Supabase's RLS becomes the tenancy mechanism, enforcing D7's `user_id` at the database rather than in a hand-rolled data-access layer.
*Rules out:* Neon; app-layer tenancy as the primary guard.
*Reverses if:* you need a Postgres feature Supabase gates behind a higher tier, or RLS proves too coarse — then move to plain managed Postgres plus app-layer tenancy.

---

**D11 — Web reads/writes book rows via Drizzle introspected; a fixed dev user until auth (M1)**
The web app connects to Postgres over the transaction pooler with a schema generated by `drizzle-kit pull` (never `push`/`generate` — Alembic stays the only DDL path, per D5). RLS with `auth.uid()` policies is created in the first book migration (`0002_book`), but until Supabase Auth exists the web app connects as the table-owner role (which bypasses RLS) and scopes every query explicitly to a seeded dev `user_id` (`00000000-…-0001`).
*Rules out:* hand-writing the web's schema; using the Supabase JS client / anon key for M1.
*Reverses if:* auth lands — then the web connects as the authenticated role, `auth.uid()` drives tenancy, and the explicit `WHERE user_id = …` becomes belt-and-suspenders rather than the guard.

---

**D12 — Tiingo for daily bars, not Finnhub**
Finnhub moved historical daily candles behind premium (403 on free keys), so it can no longer supply `bars_daily`. Tiingo's free tier provides daily EOD OHLCV with a real adjusted close (`close` + `adjClose` → `c` / `adj_c`), under a personal/internal, no-redistribution licence — the same non-commercial shape as before, so the product-licensing blocker is unchanged. Benchmark ETFs come from the same EOD path. Earnings calendar and company news (M7/M8) are left as TBD source gaps; Tiingo free covers neither. This is the `MarketDataProvider` abstraction paying off exactly as predicted ("you will switch, probably twice").
*Rules out:* Finnhub as the bars source; a single-vendor assumption for all market data.
*Reverses if:* Tiingo restricts or paywalls free EOD — then swap the `daily_bars` implementation (Stooq is the keyless fallback candidate) without touching the rest of the pipeline.

---

**D13 — Ingest stores one verbatim payload per fetch; normalize is a pure replay**
Stage ① writes the whole vendor response for a symbol as a single `raw_payloads` row, keyed by the latest session date it contains, so re-fetching the same window is a no-op (`ON CONFLICT DO NOTHING`). Numeric fields are parsed as `Decimal` and stored as JSON strings, keeping prices entirely off the float path (money invariant) while preserving exact precision. Stage ② (`bars_from_payloads`) is a pure function — no network, clock, or float — that explodes payloads into bars with the latest fetch winning on overlap; this is what makes "wipe `bars_daily`, replay from `raw_payloads`, get identical rows" a property test rather than a hope.
*Rules out:* normalizing on ingest; per-day payload rows; extracting numbers as float.
*Reverses if:* a vendor's response isn't row-per-symbol-shaped, or overlap resolution needs to consider more than fetch recency.

---

**D14 — `metrics` carries `user_id`; compute uses cents + exact Fractions**
The data-model sketch showed `metrics` without `user_id`, but contribution/weight/P&L are book-specific, so the table carries `user_id` (PK `(user_id, symbol, session_date, metric)`, RLS-keyed like the book tables) — reconciling it with invariant 4. In `worker/compute.py`, money is integer cents rounded per position (as a broker rounds), and every ratio (`day_return`, `contribution_bps`, `weight`, `day_bps`, `total_pct`, `vs_spy_bps`) is an exact `fractions.Fraction`, converted to Decimal only at storage. This is what makes `Σ contribution_bps == book day_bps` an *exact* equality (invariant 3), not a tolerance — verified in a property test with deliberately messy inputs. Compute is pure over `bars_daily` + `lots`, so it re-runs deterministically. Unrealized P&L only (lots store no sale proceeds); splits between purchase and now are a known caveat.
*Rules out:* a single shared `metrics` table without tenancy; decimal-rounded bps that don't sum; realized-P&L in M3.
*Reverses if:* the `lots` model gains sale proceeds (realized P&L), or per-user metric redundancy for shared symbol metrics (e.g. `day_return`) becomes worth splitting into a separate shared table.

---

**D15 — Assembly is a pure function; the BriefObject carries rounded display integers**
Stage ④ (`worker/assemble.py`) is pure over a `ComputeResult` — `generated_at` is injected, never `datetime.now()` — so a frozen fixture snapshots the whole object (M4's definition of done). The exact `Fraction` bps that stage ③ guarantees to sum (`Σ contribution_bps == day_bps`, invariant 3) are rounded to `int` here to satisfy the contract's `day_bps`/`contribution_bps`/`vs_spy_bps` integer types. **The rounded per-row bps need not re-sum to the rounded book `day_bps`** — the exact identity lives in `metrics`/compute (what invariant 3 and the `verify-numbers` skill protect); the object's integers are for display. `schema_version` starts at **1** (the "3" in the docs/04 example is illustrative, not history). M4 emits only the sections it can populate — `book` totals + one `attribution` section, all `tier: "full"` — and raises rather than emitting a degraded object when the book has no prior-close value; suppression/tiers (M5), tape quality (M5), claims (M6), flags (M7) and narration (M8) stay empty. Persistence upserts on `UNIQUE (user_id, session_date, kind)`, so re-assembly replaces rather than duplicates.
*Rules out:* narration or any LLM output in M4; a renderer that "corrects" the rounded-bps discrepancy; per-day duplicate brief rows.
*Reverses if:* a downstream renderer needs the per-row bps to tie exactly to the book line — then carry an extra exact field or render bps to a decimal place rather than a whole number.

---

**D16 — Suppression tiers on the row; tape quality in its own pure stage (M5)**
Each held name is tiered in assembly (docs/05): `full` if it moved >1% **or** RVOL >1.5×, `brief` in the 0.3–1% band, else `suppressed`. Suppressed names leave the attribution rows and appear only in the top-level `suppressed[]`, rendered as one roll-up line — this is what makes a quiet session's brief shorter. The `full`/`brief` split is carried on a new per-row `tier` field (`section.tier` can't, since one section mixes tiers), which bumps `schema_version` to **2**; suppressed names have no row, so the enum is only `full`/`brief`. A close brief with **no** full-tier mover is skipped entirely (`assemble_and_store` returns `None`, writes nothing); the gate is "no full-tier name," so an RVOL spike on a flat-price day still sends — slightly broader than the literal "nothing moved >1%," and deliberately so. Tape quality (`worker/tape.py`, kept separate so the M3-certified P&L compute is untouched) is pure and exact: `range_position = (c−l)/(h−l)`, null when `h==l`; `rvol = v / mean(30 prior sessions)`, excluding today and null under 30 bars — stored in `metrics`, surfaced in a `tape_quality` section for the full-tier movers only. The earnings-in-5-sessions and "carries news" tier exceptions are **not** applied yet — they need data that lands at M7/M8 — and there is a clean seam (`_tier`) to add them.
*Rules out:* per-name suppression via `section.tier`; the renderer deciding what to hide (D1); gap-fill/VWAP tape in v1 (D3); a brief that sends on brief-tier-only movement.
*Reverses if:* the whole-skip gate should track price strictly (drop the RVOL clause), or per-row `rel_strength`/distance-from-50d in §4 becomes wanted (add the fields, bump the version).

---

**D16b — Accountability loop scores through the close brief; the open brief isn't built yet (M6)**
The milestone says the close brief scores "the same day's open brief," but no open brief exists yet — so M6 builds the general emit→grade→persist engine and exercises it through the **close** brief: session D's close brief resolves the **previous** close brief's due claims (horizon 1) and emits its own. The mechanism is identical to same-day open→close scoring, which drops in unchanged once an open brief emits a horizon-0 morning claim. `claims[]`/`resolved_claims[]` already existed in the v2 object, so **no schema bump**.
*Rules out:* building a partial open brief just to satisfy the literal wording; regex over prose to recover claim history (D1).
*Reverses if:* the open brief lands — then its morning claims resolve same-day at the close with no engine change.

---

**D17 — One mechanical claim type in M6 (`relative_strength`); bars are the session clock**
`worker/claims.py` (pure emit, DB-backed resolve, kept out of the P&L compute) implements only `relative_strength` — the one claim type fully judgeable from `bars_daily` (`sym_day_return − SPY_day_return`): a **full-tier** name clearing ±1% relative earns an `up`/`down` claim, horizon 1. Resolution grades from the tape and uses `bars_daily` itself as the session clock (the horizon-th bar after emission), honouring invariant 7 without a hardcoded calendar. The `claims` table (migration `0006`) adds `session_date` (emit session — resolution is a date query, not a join) and `resolved_session` to the docs/03 sketch, and stores `brief_id` as the **object's text slug** (deterministic, available before the briefs row is written) rather than a FK to `briefs.id`; `UNIQUE (user_id, symbol, claim_type, session_date)` makes emission idempotent, and resolution skips already-graded claims. A skipped (quiet) close brief still **resolves** its due claims but **emits** none. The event-driven types (`catalyst_pending`, `supply_overhang`, `breadth`) and the every-fourth-Friday scorecard are deferred — they need data that lands at M7 — behind the same `claim_type` seam.
*Rules out:* claim types that need events/news/sector data in M6; a hardcoded trading calendar for horizons; regrading a resolved claim; emitting on a dead session.
*Reverses if:* the emission heuristic (full-tier, ±1% relative, SPY benchmark, horizon 1) proves too noisy — tune the threshold, switch to the sector benchmark, or widen horizons; the seam stays the same.
