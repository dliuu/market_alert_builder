# 07 — Decision log

Append-only. Each entry: what was decided, what it rules out, and what would reverse it.

---

**D1 — Brief-as-object, not brief-as-template**
The pipeline emits versioned JSON; web and email are renderers over it.
*Rules out:* generating HTML directly from the compute stage.
*Reverses if:* never. Retrofitting this means parsing your own prose to recover the claim history.

---

**D2 — The LLM never produces a number**
Narration writes prose only; figures are substituted from the object.
*Rules out:* asking the model to summarise raw market data.
*Reverses if:* never, for a tool you act on. A hallucinated basis point is a worse failure than a missing paragraph.

---

**D3 — Tape quality runs on daily OHLCV**
Range position is exact from daily O/H/L/C; RVOL uses 30-day average volume.
*Rules out:* gap-fill behaviour and VWAP in v1.
*Reverses if:* you notice yourself repeatedly wanting to know whether a gap filled. Then buy minute bars (~$29/mo).

---

**D4 — Two services, Postgres as the shared surface**
Next.js for UI/auth/billing/email templates; Python for the pipeline.
*Rules out:* a single-language monolith; an internal REST API between the two.
*Reverses if:* this stays single-user forever, in which case a Python monolith with Jinja is less to operate.

---

**D5 — Python owns the schema exclusively**
Alembic is the only migration path; the web app introspects and never issues DDL.
*Rules out:* Drizzle or Prisma migrations.
*Reverses if:* never. Two ORMs owning one schema is the most reliable way to lose a weekend.

---

**D6 — One HTTP call between services: `/api/render/:brief_id`**
So the email template has exactly one source (React Email in the web app).
*Rules out:* a parallel MJML template in Python.
*Reverses if:* the web app's availability becomes the pipeline's bottleneck. Fallback is a plaintext-only send.

---

**D7 — `user_id` on every table from the first migration**
Even during single-user development.
*Rules out:* nothing. Costs one column.
*Reverses if:* never.

---

**D8 — End-of-day data, not real-time**
The close brief is EOD-native; the open brief uses prior close plus delayed pre-market.
*Rules out:* intraday alerts, live dashboards.
*Reverses if:* you take the product commercial and buy a real-time redistribution licence — a business decision, not a technical one.

---

**D9 — No intraday alerts**
*Rules out:* push notifications, a third send.
*Reverses if:* never. It changes a briefing into a monitor, which is a different product with worse habits attached.

---

**D10 — Supabase for Postgres, not Neon**
Managed Postgres from Supabase. The worker still owns the schema via Alembic against the direct connection; Supabase's RLS becomes the tenancy mechanism, enforcing D7's `user_id` at the database rather than in a hand-rolled data-access layer.
*Rules out:* Neon; app-layer tenancy as the primary guard.
*Reverses if:* you need a Postgres feature Supabase gates behind a higher tier, or RLS proves too coarse — then move to plain managed Postgres plus app-layer tenancy.

---

**D11 — Web reads/writes book rows via Drizzle introspected; a fixed dev user until auth (M1)**
The web app connects to Postgres over the transaction pooler with a schema generated by `drizzle-kit pull` (never `push`/`generate` — Alembic stays the only DDL path, per D5). RLS with `auth.uid()` policies is created in the first book migration (`0002_book`), but until Supabase Auth exists the web app connects as the table-owner role (which bypasses RLS) and scopes every query explicitly to a seeded dev `user_id` (`00000000-…-0001`).
*Rules out:* hand-writing the web's schema; using the Supabase JS client / anon key for M1.
*Reverses if:* auth lands — then the web connects as the authenticated role, `auth.uid()` drives tenancy, and the explicit `WHERE user_id = …` becomes belt-and-suspenders rather than the guard.

---

**D12 — Tiingo for daily bars, not Finnhub**
Finnhub moved historical daily candles behind premium (403 on free keys), so it can no longer supply `bars_daily`. Tiingo's free tier provides daily EOD OHLCV with a real adjusted close (`close` + `adjClose` → `c` / `adj_c`), under a personal/internal, no-redistribution licence — the same non-commercial shape as before, so the product-licensing blocker is unchanged. Benchmark ETFs come from the same EOD path. Earnings calendar and company news (M7/M8) are left as TBD source gaps; Tiingo free covers neither. This is the `MarketDataProvider` abstraction paying off exactly as predicted ("you will switch, probably twice").
*Rules out:* Finnhub as the bars source; a single-vendor assumption for all market data.
*Reverses if:* Tiingo restricts or paywalls free EOD — then swap the `daily_bars` implementation (Stooq is the keyless fallback candidate) without touching the rest of the pipeline.

---

**D13 — Ingest stores one verbatim payload per fetch; normalize is a pure replay**
Stage ① writes the whole vendor response for a symbol as a single `raw_payloads` row, keyed by the latest session date it contains, so re-fetching the same window is a no-op (`ON CONFLICT DO NOTHING`). Numeric fields are parsed as `Decimal` and stored as JSON strings, keeping prices entirely off the float path (money invariant) while preserving exact precision. Stage ② (`bars_from_payloads`) is a pure function — no network, clock, or float — that explodes payloads into bars with the latest fetch winning on overlap; this is what makes "wipe `bars_daily`, replay from `raw_payloads`, get identical rows" a property test rather than a hope.
*Rules out:* normalizing on ingest; per-day payload rows; extracting numbers as float.
*Reverses if:* a vendor's response isn't row-per-symbol-shaped, or overlap resolution needs to consider more than fetch recency.

---

**D14 — `metrics` carries `user_id`; compute uses cents + exact Fractions**
The data-model sketch showed `metrics` without `user_id`, but contribution/weight/P&L are book-specific, so the table carries `user_id` (PK `(user_id, symbol, session_date, metric)`, RLS-keyed like the book tables) — reconciling it with invariant 4. In `worker/compute.py`, money is integer cents rounded per position (as a broker rounds), and every ratio (`day_return`, `contribution_bps`, `weight`, `day_bps`, `total_pct`, `vs_spy_bps`) is an exact `fractions.Fraction`, converted to Decimal only at storage. This is what makes `Σ contribution_bps == book day_bps` an *exact* equality (invariant 3), not a tolerance — verified in a property test with deliberately messy inputs. Compute is pure over `bars_daily` + `lots`, so it re-runs deterministically. Unrealized P&L only (lots store no sale proceeds); splits between purchase and now are a known caveat.
*Rules out:* a single shared `metrics` table without tenancy; decimal-rounded bps that don't sum; realized-P&L in M3.
*Reverses if:* the `lots` model gains sale proceeds (realized P&L), or per-user metric redundancy for shared symbol metrics (e.g. `day_return`) becomes worth splitting into a separate shared table.

---

**D15 — Assembly is a pure function; the BriefObject carries rounded display integers**
Stage ④ (`worker/assemble.py`) is pure over a `ComputeResult` — `generated_at` is injected, never `datetime.now()` — so a frozen fixture snapshots the whole object (M4's definition of done). The exact `Fraction` bps that stage ③ guarantees to sum (`Σ contribution_bps == day_bps`, invariant 3) are rounded to `int` here to satisfy the contract's `day_bps`/`contribution_bps`/`vs_spy_bps` integer types. **The rounded per-row bps need not re-sum to the rounded book `day_bps`** — the exact identity lives in `metrics`/compute (what invariant 3 and the `verify-numbers` skill protect); the object's integers are for display. `schema_version` starts at **1** (the "3" in the docs/04 example is illustrative, not history). M4 emits only the sections it can populate — `book` totals + one `attribution` section, all `tier: "full"` — and raises rather than emitting a degraded object when the book has no prior-close value; suppression/tiers (M5), tape quality (M5), claims (M6), flags (M7) and narration (M8) stay empty. Persistence upserts on `UNIQUE (user_id, session_date, kind)`, so re-assembly replaces rather than duplicates.
*Rules out:* narration or any LLM output in M4; a renderer that "corrects" the rounded-bps discrepancy; per-day duplicate brief rows.
*Reverses if:* a downstream renderer needs the per-row bps to tie exactly to the book line — then carry an extra exact field or render bps to a decimal place rather than a whole number.

---

**D16 — Suppression tiers on the row; tape quality in its own pure stage (M5)**
Each held name is tiered in assembly (docs/05): `full` if it moved >1% **or** RVOL >1.5×, `brief` in the 0.3–1% band, else `suppressed`. Suppressed names leave the attribution rows and appear only in the top-level `suppressed[]`, rendered as one roll-up line — this is what makes a quiet session's brief shorter. The `full`/`brief` split is carried on a new per-row `tier` field (`section.tier` can't, since one section mixes tiers), which bumps `schema_version` to **2**; suppressed names have no row, so the enum is only `full`/`brief`. A close brief with **no** full-tier mover is skipped entirely (`assemble_and_store` returns `None`, writes nothing); the gate is "no full-tier name," so an RVOL spike on a flat-price day still sends — slightly broader than the literal "nothing moved >1%," and deliberately so. Tape quality (`worker/tape.py`, kept separate so the M3-certified P&L compute is untouched) is pure and exact: `range_position = (c−l)/(h−l)`, null when `h==l`; `rvol = v / mean(30 prior sessions)`, excluding today and null under 30 bars — stored in `metrics`, surfaced in a `tape_quality` section for the full-tier movers only. The earnings-in-5-sessions and "carries news" tier exceptions are **not** applied yet — they need data that lands at M7/M8 — and there is a clean seam (`_tier`) to add them.
*Rules out:* per-name suppression via `section.tier`; the renderer deciding what to hide (D1); gap-fill/VWAP tape in v1 (D3); a brief that sends on brief-tier-only movement.
*Reverses if:* the whole-skip gate should track price strictly (drop the RVOL clause), or per-row `rel_strength`/distance-from-50d in §4 becomes wanted (add the fields, bump the version).

---

**D16b — Accountability loop scores through the close brief; the open brief isn't built yet (M6)**
The milestone says the close brief scores "the same day's open brief," but no open brief exists yet — so M6 builds the general emit→grade→persist engine and exercises it through the **close** brief: session D's close brief resolves the **previous** close brief's due claims (horizon 1) and emits its own. The mechanism is identical to same-day open→close scoring, which drops in unchanged once an open brief emits a horizon-0 morning claim. `claims[]`/`resolved_claims[]` already existed in the v2 object, so **no schema bump**.
*Rules out:* building a partial open brief just to satisfy the literal wording; regex over prose to recover claim history (D1).
*Reverses if:* the open brief lands — then its morning claims resolve same-day at the close with no engine change.

---

**D17 — One mechanical claim type in M6 (`relative_strength`); bars are the session clock**
`worker/claims.py` (pure emit, DB-backed resolve, kept out of the P&L compute) implements only `relative_strength` — the one claim type fully judgeable from `bars_daily` (`sym_day_return − SPY_day_return`): a **full-tier** name clearing ±1% relative earns an `up`/`down` claim, horizon 1. Resolution grades from the tape and uses `bars_daily` itself as the session clock (the horizon-th bar after emission), honouring invariant 7 without a hardcoded calendar. The `claims` table (migration `0006`) adds `session_date` (emit session — resolution is a date query, not a join) and `resolved_session` to the docs/03 sketch, and stores `brief_id` as the **object's text slug** (deterministic, available before the briefs row is written) rather than a FK to `briefs.id`; `UNIQUE (user_id, symbol, claim_type, session_date)` makes emission idempotent, and resolution skips already-graded claims. A skipped (quiet) close brief still **resolves** its due claims but **emits** none. The event-driven types (`catalyst_pending`, `supply_overhang`, `breadth`) and the every-fourth-Friday scorecard are deferred — they need data that lands at M7 — behind the same `claim_type` seam.
*Rules out:* claim types that need events/news/sector data in M6; a hardcoded trading calendar for horizons; regrading a resolved claim; emitting on a dead session.
*Reverses if:* the emission heuristic (full-tier, ±1% relative, SPY benchmark, horizon 1) proves too noisy — tune the threshold, switch to the sector benchmark, or widen horizons; the seam stays the same.

---

**D18 — M7 flags: pure thresholds + `last_seen` rate limit, exercised through the close brief on synthetic data**
`worker/flags.py` (pure threshold core + DB layer, kept out of the P&L compute like `claims`/`tape`) computes two mechanisms into the object's existing top-level `flags[]`: **position risk** (runway < 6q, dilution > 15% YoY, earnings ≤ ~5 sessions, a lockup supply event ≤ 7 days, short interest > 20%) and the **correlation flag** (single name > 20%, sector > 50%, or mean 20d pairwise correlation > 0.75). The contract already defined all seven flag types, so **no schema bump** (still v2). Migration `0007` adds `fundamentals` + `events` (shared market data, **no `user_id`**, like `bars_daily`) and `flags` (`user_id`, RLS, `UNIQUE NULLS NOT DISTINCT (user_id, flag_type, symbol, sector_id)`). The correlation flag's once-a-week cap (docs/05) is enforced by `flags.last_seen` — the last session it was *surfaced*; capped types (`concentration`, `correlation`) re-surface only when `session_date − last_seen ≥ 7 days`, and `last_seen` is written **only when the brief actually sends**, so a quiet skipped session spends no budget. Position-risk types aren't capped. Per D16b's precedent, the engine is exercised through the **close** brief (the open brief's §6 exposure_check isn't built); the same `flags[]` renders there unchanged when the open brief lands. **Synthetic-only** (user decision): `fundamentals`/`events` are seeded, not ingested — real Tiingo/EDGAR earnings & fundamentals and a short-interest source stay deferred (docs/02 TBD gaps), and `short_interest` therefore has a live threshold but no feed in v1. Earnings/supply proximity is measured in **calendar days** (`exchange_calendars` isn't a worker dep and a future date has no bars to count); the predicates take a scalar so switching to true session-counting at M10 is a one-line DB-layer change.
*Rules out:* a schema bump for flags; `user_id` on the shared fundamentals/events tables; real earnings/fundamentals/short-interest ingest in M7; a rate limit that burns budget on unsent briefs; building a partial open brief just to place §6.
*Reverses if:* the calendar lands (swap calendar-day proximity for session-counting); the weekly cap should track calendar weeks rather than a rolling 7 days; or persisting `corr_20d` to `metrics` (rather than only the flag `value`) becomes worthwhile.

*Superseded in part by D23 (M14):* the open brief's §6 is now built, so flags **moved** there rather than rendering in both — one `last_seen` clock cannot serve two briefs without the earlier fire silently spending the other's weekly budget. `surface_flags` also stopped taking a `ComputeResult`.

**D19 — M8 narration: a `str → str` seam, prose-only, non-fatal by construction**
`worker/narrate.py` is stage ⑤. The whole stage hangs off a `Narrator = Callable[[str], str]` (prompt in, raw JSON out): `build_prompt` / `parse_narration` / `apply_narration` are pure and unit-tested without a network, and `default_narrator()` binds the one Claude call at the edge — returning **`None` when `ANTHROPIC_API_KEY` is unset**, which *is* the "revoke the key" path in the milestone. `narrate_and_apply` wraps the call in a broad `except` that returns the object **unchanged** on any failure (no key, auth error, timeout, malformed JSON): a brief with no prose is valid and sendable; a brief that didn't send is not (docs/02). This is the rare case where the try/except is the feature, not a hedge (contra CLAUDE.md), and it's covered by a test that raises from the narrator. The parser enforces invariant 2 mechanically — any narration string containing a **digit** is dropped (a digit is a hallucinated figure; the tables carry every number), as is any `why` key not matching an attribution symbol (docs/04 "drop any key that doesn't match"). Only `one_thing` and the attribution rows' `why` are filled; `sector_notes` (docs/04) waits on a sector section the close brief doesn't build yet. The object shape didn't change — `one_thing`/`why` already existed in v2 — so **no schema bump** and the M4 fixture snapshot is untouched (pure `assemble()` never narrates). Wiring: `assemble_and_store` gains a keyword-only `narrator` defaulting to `None` (off), so every existing test and the DB integration suite stay hermetic — no accidental live calls; the CLI (`brief`, `--no-narrate` to opt out) passes `default_narrator()`. Narration runs **after** the skip check, so a quiet brief spends no tokens, and **before** the store, so the persisted body carries the prose. Model is `claude-opus-4-8` (config `NARRATION_MODEL`), via the official `anthropic` SDK, `max_tokens=1024`, no thinking — it writes one paragraph and a sentence per name.
*Rules out:* a schema bump for narration; the LLM emitting any figure (dropped at the seam); a narration failure ever blocking a send; live Claude calls inside the test suite (narrator is off unless wired); building a sector section just to place `sector_notes`.
*Reverses if:* a real company-news feed lands (feed headlines into `build_prompt` per docs/04's "give it the news headlines"); a sector section is built (add `sector_notes`); or the digit-drop proves too blunt for legitimate prose (relax to a smarter figure detector).

**D20 — M10 scheduler: a daily heartbeat that fires every calendar day, self-reschedules off the real close, and pings on every run**
`worker/calendar.py` wraps `exchange_calendars` (`XNYS`) — now a worker dependency, so invariant 7 is finally load-bearing rather than aspirational and the M7/D18 "when the calendar lands (M10)" note is discharged. `worker/scheduler.py` runs a `BlockingScheduler` with a **single self-rescheduling one-shot `DateTrigger`**, not a cron: each run computes the *next* fire as that day's `close_or_standard + SEND_DELAY_MINUTES`, so a **half-day moves the send automatically** (13:45 ET, not 16:45) without a special case (docs/02). The scheduler **fires every calendar day**, not only trading days: on a session it runs the close pipeline and sends; on a weekend or holiday it does nothing but still **pings Healthchecks success** — so the dead-man's switch stays green on a *correctly-skipped* holiday (Labor Day 2026-09-07 in the DoD) rather than reading a holiday as a missed check-in. An uncaught failure pings `<url>/fail` and re-raises; a dead worker simply stops pinging and the check goes red (docs/02). Both ping helpers swallow network errors by design — a monitoring outage must never take down a send (the try/except is the feature, like D19). EOD-lag (your call): `ensure_todays_bars` **polls Tiingo** for today's bar up to `BAR_POLL_TIMEOUT_S` (default 20 min) at `BAR_POLL_INTERVAL_S`, reusing idempotent ingest (D13); if the bar never lands, `compute_and_store` raises → `/fail` alert, and no **stale** brief is sent (docs/06: "a stale brief arriving at 11am is worse than none"). `book_symbols` unions the held names with the benchmark, fixing a latent gap where the manual `backfill` omitted `SPY` (the vs-SPY line needs it even when it isn't in the book). The pure fire-time math (`fire_time`/`next_fire`) and the go/no-go body (`run_session_job`, which takes an injected `now_utc`) are unit-tested without a clock, network, or DB; the blocking loop and a real send are only exercised live. Deploy is `apps/worker/{Dockerfile,fly.toml}` — one always-on Fly machine, no HTTP service (no cold starts, docs/02), with `alembic upgrade head` as the `release_command` (invariant 1). `schedule --once` is a **live** run (it will send), so `--dry-run` (prints the next fire times, touches nothing) is the safe smoke check. **The box stays unticked** until the five-session soak — including the holiday skip — is observed on the live deploy; that verification is inherently multi-day and manual.
*Rules out:* a fixed-time cron that ignores half-days; a weekday-only cron that reads a holiday as a failed check-in; sending a stale brief when EOD data is late; hardcoding holidays or a 16:00 close (invariant 7); scheduling the open brief (no pre-market pipeline exists yet).
*Reverses if:* ~~the open-brief pipeline lands (add its own fire at 08:15 staged per docs/02)~~ — **discharged by D23 (M14, built)**; the every-calendar-day heartbeat proves noisy on Healthchecks (switch to a weekday cadence with a holiday-aware grace); or firing off a single machine needs an active/standby leader-lock (Fly can run two).

**D21 — M11 return attribution: shared (not user-keyed) tables, a walking-skeleton two-factor model, and a scheduler-ready CLI**
Return attribution decomposes a name's daily move into **market + theme + idiosyncratic** (additive, in bps). Three decisions lock the design (full spec: `docs/superpowers/specs/2026-08-13-m11-attribution-design.md`). **(1) Attribution outputs are shared, keyed `(symbol, trade_date, model_version)` with no `user_id`** — the decomposition is a property of the symbol and the theme model, identical for every holder, so it follows the `bars_daily`/`fundamentals`/`events` precedent (D18) rather than the user-keyed `metrics` table (D14); this is a deliberate carve-out from invariant 4, the same one the market-data tables already take, and it keeps compute cost per-symbol not per-user (docs/02 scaling shape). Salience ranking (M13) is then a read-time filter of shared attribution over a user's held names. **(2) M11 ships the *known-unstable* raw two-factor model** (`r = α + β_m·market + β_theme·basket_LOO + ε`, plain OLS, 120d, all days) over point-in-time, equal-weight, **leave-one-out** baskets (`r_LOO(X) = (n·r_full − r_X)/(n−1)`, analytic for equal weight). Market and theme are ~0.85 correlated so the β's *will* be unstable — that is expected and is exactly what M12's sequential orthogonalization fixes; M11 only proves the pipeline (author's call: reconciliation before econometrics). Orthogonalization, Huber, EWMA, MAD scaling, contaminated-day exclusion, capping, fractional multi-theme loadings, and diagnostics are **M12**; all Layer-5 consumers and the BriefObject `schema_version` bump are **M13**. **(3) CLI-driven but scheduler-ready:** stages are thin functions over `(conn, trade_date, now_utc, model_version)` with an **injected clock** (the D20 `run_session_job` pattern), wrapped by `attribution refit | score --pm | reconcile --am` now and by scheduler fires in M13 with no logic change. The PM-synthesize (today's bar from `get_latest_prices` minute data, `provisional`) / AM-reconcile (official `adj_c` bar; correct-if-`|Δ|>tol`, mark `revised`) plumbing is real and tested in M11 — silent synthetic/official drift would slowly corrupt every fitted β. New provider `FdnProvider` (fdnpy) is added **alongside** Tiingo behind `MarketDataProvider` (D12's "you will switch, probably twice"), extended with `latest_minute()`; migration `0009_attribution` adds `themes`/`theme_members` (PIT, shared, seeded like M7's fundamentals) plus `basket_returns`/`attribution_fits`/`attribution`. Returns come from `adj_c` (ex-div/split gaps already removed); regression is float ("off the money path", like `flags.mean_pairwise_corr`), quantized to `Decimal` at storage. Cold start (`n_obs < 40`) shrinks β toward the theme median and marks `provisional`. Validation is in the DoD from day one: additivity property test, null test (shuffled calendar → flat residuals, catches look-ahead), known-answer (earnings-day → large residual), and a frozen-fixture snapshot.
*Rules out:* putting attribution in the user-keyed `metrics` table; orthogonalization/robust-scaling/consumers in M11; a BriefObject bump before M13; `datetime.now()` inside a stage (breaks the scheduler seam and hermetic tests); recomputing history against current theme membership (PIT is load-bearing); a name regressed on a basket containing itself (leave-one-out is mandatory).
*Reverses if:* attribution ever needs per-user parameters (then it splits like `metrics` did in D14); the raw two-factor residual proves usable enough that M12's orthogonalization is deferred; or the scored universe grows enough that leave-one-out per name needs the O(1) analytic form replaced by a stored per-(theme, excluded-symbol) return.

**D22 — M14/M15 open brief: a second `kind` on the same object, skeleton-on-cached-data then feeds-synthetic-first**
The open brief (docs/01: 08:15 ET, forward-looking, no P&L) is built as the **second `kind` on the one versioned BriefObject** (D1), not a separate object — the `kind`, section-`id` (`overnight_tape`/`premarket`/`calendar`/`sector_setup`/`exposure_check`), and claim/flag machinery were already in the contract. It splits into two milestones along a hard data boundary. **M14 (skeleton)** builds §1/§4/§5/§6 entirely from **already-cached** data (prior-close bars, `events`, M7 `flags` — the open brief is finally §6's intended home, discharging D18), via a **new pure `worker/assemble_open.py`** that does *not* go through the P&L `ComputeResult` path, leaving `assemble.py` and the M4/invariant-3 machinery untouched. The open brief carries **no P&L**, so **`book` is made nullable** and omitted (chosen over carrying book value or forking the object) — a shape change that **bumps `schema_version`** (coordinated with M13's bump; landing order assigns the number, old renderers kept per docs/04). It gets its **own React Email template** selected by `kind` at the one `/api/render` call (D6), and a **second staged scheduler fire** (ingest 08:00 → assemble 08:10 → send 08:15) generalizing D20's single self-rescheduling one-shot into a per-kind schedule — **discharging D20's "the open-brief pipeline lands → add its own fire at 08:15"** reversal note. The open brief **always sends** (docs/05: "nothing overnight" is information); §2/§3 render as an omitted-note in M14. **M15 (feeds)** adds §2 overnight tape (ES/NQ, 10Y, DXY, VIX, WTI, foreign proxies) and §3 pre-market names (>1% or news; pre %, gap in **dollars**, pre-market volume as a multiple — explicitly **not** the 30d RVOL, since pre-market volume is too thin, D3/docs/05), landing in the **shared `quotes` table** (no `user_id`, `extended_last`/`extended_v` for held names; macro symbols as shared reference series) behind the `MarketDataProvider` seam. Per the licensing reality (D8), M15 is built against **synthetically-seeded** data (the M7 pattern) and **swaps to live fdnpy premium** (latest-prices / futures / index / forex) once licensed — a business decision, not a code blocker; no real-time data and no intraday send, so **D9 stands**. M15 also lands the **horizon-0 morning claim** resolved at the same day's close — the first live open→close accountability loop the D16b engine was built for — and bumps `schema_version` for the §3 pre-market row fields. Attribution-residual salience (M13) upgrades §1's lead when both land: a documented cross-feature join, not a dependency.
*Rules out:* a separate open-brief object (D1); putting P&L in the open brief; a single all-sections milestone coupled to data licensing; blocking M15 on procurement; real-time feeds or a third intraday send (D9); duplicating the close assembler.
*Reverses if:* the open brief ever needs a book/P&L view (un-nullable `book`, or a dedicated open-book field); the per-kind schedule needs to become two independent triggers or a leader-lock (D20's own reversal); or delayed pre-market data proves unlicensable even commercially, in which case §3 falls back to a prior-close-gap-at-open proxy and §2 to EOD macro closes.

**D23 — M14 as built: what the open-brief skeleton forced that the plan didn't anticipate**
D22 set the shape; implementation surfaced five decisions it doesn't cover.

**(1) The contract bump is wider than `book`.** `row` carried only close-brief columns, so §4/§5 had nowhere to write: it gains `label`/`event_type`/`occurs_at`/`tag` (calendar) and `sector_id`/`name`/`benchmark_symbol`/`ret_5d`/`vs_spy_5d`/`premarket` (sector setup), and `symbol` becomes optional because a macro release names no security. `row` also gained the `additionalProperties: false` it was the only def to lack — it had been *silently dropping* unknown keys, so a typo'd field would have shipped as a null. Separately, **no stored body had ever validated against the JSON Schema**: codegen types a non-required property as `T | None = None`, so Pydantic emits nulls the schema's own `type`/`enum` rejects, and only the TypeScript side follows the schema. `tier` had been null in every body since M5. Both are now explicitly nullable and `test_contract_schema.py` checks stored fixtures against the canonical schema directly — the only place both halves of the contract meet the same bytes.

**(2) §6's flags move out of the close brief rather than being shared.** `flags.last_seen` is a single weekly clock (docs/05: one mention per week). With both briefs surfacing, the 08:15 fire spends the budget and the 16:45 one silently renders nothing — a timing-dependent bug invisible in tests that run one brief. So `assemble.py` stops surfacing and recording flags entirely and the close template's block is removed; `flags[]` stays in the shape, empty. This is what D18 anticipated ("the close brief hosted them only because the open brief's §6 isn't built"). `surface_flags` correspondingly takes `symbols` + `name_weights` instead of a `ComputeResult`, which also drops `flags.py`'s last import from `compute` — the open brief must never run the P&L path, because that path raises on a missing bar and the open brief always sends.

**(3) The open brief emits and resolves no claims in M14.** Emitting: nothing directional is judgeable from cached setup (the horizon-0 morning claim needs the pre-market signal, M15). Resolving is the subtler half — calling `resolve_due_claims` at 08:15 *works*, and that is the trap: it would consume the due claims before the close brief's §7 could report them. Resolution stays in the close brief (D16b, unchanged).

**(4) `events` needed a migration, and had no writer at all.** M7 built the table for the lockup flag alone, so it rejects half of §4: no `ex_div` in the CHECK, `symbol` NOT NULL, and no label (§4 renders "CPI (Jul)", not "macro"). `0010_open_events` widens it and adds a `UNIQUE NULLS NOT DISTINCT` key so seeding is re-runnable. `worker/events_seed.py` is the first thing ever to write there, emitting the **vendor calendar shape** so the eventual swap is a provider call. The live source exists (fdnpy `get_earnings_calendar` / `get_dividends_calendar` / `get_economic_calendar`, retiring two of docs/02's TBDs as *source* questions) but is Premium tier with redistribution behind Enterprise — the same D8 gate M15 defers, so wiring it would import M15's blocker into the milestone built to ship without one.

**(5) The open fire is wall-clock, not a second delay on D20's anchor.** The close fires at the real session close plus a delay, which is what moves it on a half-day; 08:15 ET must *not* move. So it converts through `America/New_York` (invariant 8) and skips non-sessions — the close fire keeps the daily heartbeat because it carries the dead-man's switch, and the open brief has nothing to say on a holiday. Verified on the real calendar: half-day Fri 2026-11-27 fires close at 13:45 ET, open at 08:15 ET. It stays a **single** self-rescheduling one-shot; `next_kind_fire` walks both schedules so ordering is explicit rather than two timers racing.

*Rules out:* sharing the weekly flag budget across both briefs; resolving claims in the morning; running compute just to obtain weights; a second delay-based fire for the open brief; two independent scheduler triggers; paying for a Premium calendar feed to ship M14; trusting the generated Pydantic as the contract.
*Reverses if:* a flag turns out to be genuinely close-relevant (the cap then needs a per-kind budget — a `flags` schema change); the calendar feed is licensed (§4 swaps behind the provider seam without touching the section); or the per-kind schedule needs independent triggers or a leader-lock (D20's own reversal).

**D28 — M15 pre-market: a real `quotes` table, a deterministic synthetic feed, and horizon-0 as an engine change**
*(Numbered D28, not D24: M13 landed upstream while M15 was in flight and took
D24–D27. This entry was written as D24 and renumbered at integration time.)*
§2 (overnight tape) and §3 (pre-market names) run on a **new `quotes` table** —
migration `0011_quotes`. The design spec said the feeds needed no migration
because `quotes` already existed; it never did (`docs/03` sketched it, `0003`
created only `raw_payloads`/`bars_daily`), the same shape of error M14 found with
`events`. It is keyed **`(symbol, session_date)`** rather than the sketch's
`(symbol, captured_at)`: every read is "the capture for session D", and the
session key makes re-seeding idempotent. Shared, no `user_id` (D18/D21).
Data comes from `SyntheticPremarketProvider` — deterministic by hash over
`(symbol, session_date)`, never `random`, so a seeded morning is
snapshot-testable — behind four premium pre-market methods a licensed
fdnpy feed will implement (`get_latest_prices` / `get_futures_prices` /
`get_index_quotes` / `get_forex_quotes`). One ingest function serves both, which
is what makes the swap a constructor change (D8 stays a business call).
§3's volume multiple is **pre-market-specific** — this morning's `extended_v`
against the mean of the prior sessions' captures — never the 30-day RVOL, which
over a pre-market tape is a number that looks meaningful and isn't (D3).
The `>1% **or carrying news**` threshold ships half-wired: `clears_threshold`
takes `has_news` and nothing sets it, because there is no news feed (docs/02:
Premium, unwired) — the D18 `short_interest` precedent.
The **horizon-0 morning claim** is a genuine change to the D17 engine, not a
`claim_type` seam ride: the contract pinned `horizon_sessions` to `minimum: 1`,
`resolve_due_claims` read only `session_date < :session_date`, and
`_resolve_session` offset by `horizon - 1`. Resolution now admits same-session
claims and, once that session has a bar, grades horizon 0 **open→close on the
emit session itself** — `(c − o) / o` for both the name and the benchmark — not
close-to-close and not the emit session's own bar as first shipped. Close-to-close
(D-1's close vs. D's close) contains the pre-market gap `emit_premarket_gap`
claimed as a sub-interval, so a name that gapped up pre-market and fully faded
intraday still graded "correct" — the gap is what the claim is *about*, so it
cannot also be what grades it. Horizon-1+ claims are untouched, still graded
close-to-close, and still excluded from their own session by `_resolve_session`,
which is asserted by a regression test (`test_claims.py`/`test_claims_db.py`
unmodified). The open brief emits and **never resolves** — resolving at 08:15
would consume the due claims before the close brief's §7 could report them.
`schema_version` bumps to **4** (§2 `level`/`overnight_pct`/`overnight_abs`, §3
`pre_pct`/`gap_cents`/`premarket_vol_mult`, the claim changes); narration gains a
`tape_read` key that lands in §2's existing `note`, so the read paragraph costs
no schema surface and inherits the digit guard.

**§2 is marked synthetic, and the tape's bootstrap seed is scoped to the tape.**
Final-pass review (post-ship) found two gaps this entry hadn't recorded.
First, `constants.TAPE_SEED_LEVELS` — plausible nominal levels for the six macro
symbols plus the five foreign proxies — ships invented market levels to a
reader with nothing telling them so. Nothing ingests bars for futures, yield, or
forex series, and the tape's own history is itself seeded from this same
recursion, so without a seed §2 has no base to gap from on any run, ever
(confirmed empirically: 0 of the tape symbols ever carry a `bars_daily` row).
It is deliberately the **lowest-priority** source in `ingest_premarket_for_session`
— a real prior capture, once one exists, always overwrites it — and it is
reflected in the object: while `constants.PREMARKET_FEED_IS_SYNTHETIC` is True,
`assemble_open` adds `"overnight_tape.synthetic"` to `data_quality.stale`
whenever §2 has rows, and both renderers key a header marker off that one entry.
Second, that seed lived in one `closes` dict shared between the held-name fetch
and the tape fetch, so a user holding one of the five foreign-proxy ETFs
directly (EWT, say) with no `bars_daily` row yet — a brand-new holding, or a
failed EOD ingest — picked up the seed's invented level as their §3 base and
could emit a horizon-0 claim off it. `ingest_premarket_for_session` now builds
two disjoint closes dicts and ingests held names and the tape in two separate
calls; a held name's base comes from `bars_daily` alone, so a symbol with no
real prior close is omitted, never invented, exactly as
`worker/providers/synthetic.py` already promised for every other symbol.

**The pre-market seam turned out to need its own protocol.** The plan (like the
design spec) had the four premium methods widening `MarketDataProvider` itself.
That broke `mypy --strict` — clean at the milestone's base, 6 errors after —
because protocols are structural: `TiingoProvider`, the EOD provider, satisfied
the narrower `MarketDataProvider` fine, but widening that one protocol to also
demand `get_latest_prices`/`get_futures_prices`/`get_index_quotes`/`get_forex_quotes`
made `TiingoProvider` stop conforming, and it structurally cannot serve pre-market
prints — there's no vendor call to add. The four methods live instead on a
separate `PremarketProvider` protocol (`worker/providers/base.py`): `FdnProvider`
is intended to satisfy both once licensed, `SyntheticPremarketProvider` only the
pre-market one, and `ingest_premarket` takes a `PremarketProvider`. One protocol
per capability was the fix; one protocol for "every provider" was the wrong shape
the moment two providers only partially overlap.

**The `claims` table needed its own migration, separate from the contract bump.**
Contract v4 widened `brief-object.schema.json`'s claim-type enum to admit
`premarket_gap` and dropped `horizon_sessions`' `minimum` to 0, but the `claims`
table carries its own CHECK constraints from migration `0006` —
`claim_type IN ('catalyst_pending', 'relative_strength', 'supply_overhang',
'breadth')` and `horizon_sessions >= 1` — which the contract bump never touched;
Python owns the schema (invariant 1), and a JSON Schema edit is not a migration.
Migration `0012_claims_premarket_gap` widens both CHECKs to match. The general
lesson: a contract enum and a database CHECK are two separate sources of truth,
and changing one does not change the other — the same shape of gap D23(1) found
between the generated Pydantic and the canonical schema, one level down the
stack.
**Claim grading splits by claim shape, because the two claim types are about
different things.** M13 landed upstream mid-milestone and re-pointed horizon-≥1
grading at the *sign of the realized residual* (D24) so beta earns no credit.
The horizon-0 morning claim deliberately does **not** follow it there, for two
reasons that are properties of the claim rather than conveniences: it is emitted
at **08:15**, when that session's attribution row does not exist — it isn't
produced until the PM score runs after the close, and the grade has to land in
that same evening's close brief; and it is explicitly a **price** call ("this
gap holds into the close"), not a factor-adjusted one, so residualizing it would
grade a different claim than the one the brief made to the reader. `_grade` is
therefore a two-line dispatch over `_grade_open_close` (horizon 0) and
`_grade_relative` (horizon ≥ 1), with `_verdict` shared so what counts as
vindicated cannot drift between them. M13's residual grading replaces
`_grade_relative`'s body and touches nothing else.
*Rules out:* a `quotes` table keyed by capture timestamp; RVOL over pre-market
volume; the open brief resolving claims; a section that knows which provider
filled `quotes`; blocking §2/§3 on the data licence; one `MarketDataProvider`
protocol widened to cover pre-market data; assuming a contract enum bump reaches
a table's CHECK constraints without its own migration; grading a horizon-0 claim
on anything but the open→close interval it claimed; residualizing a claim made
before any attribution exists for the session; a shared closes dict that lets
the tape's bootstrap seed answer for a held name.
*Reverses if:* the premium pre-market licence lands (swap the provider and flip
`constants.PREMARKET_FEED_IS_SYNTHETIC` — `TAPE_SEED_LEVELS` and the
`data_quality.stale` marker both retire with no renderer change); a news feed
lands (`has_news` starts firing with no other change); §1's salience upgrades
from the largest gap to the largest overnight `|resid_z|` now that M13's
attribution has landed — a change to one sort key in `_premarket`; or a
same-morning attribution row ever exists, which would let the horizon-0 claim
be residualized like every other type.
